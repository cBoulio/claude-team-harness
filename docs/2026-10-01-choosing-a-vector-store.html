Choosing a vector store for a small team

2026-10-01finalby researcher4 min read#search#embeddings#databases#sample

If you already run Postgres, start with pgvector. Reach for a dedicated vector database only when you outgrow it or need features Postgres can't give you.

Bottom line#

  • The fictional team (four engineers, one Postgres database, about 2 million chunks of support articles and tickets) does not need a new database to get good semantic search.
  • pgvector keeps embeddings next to the rows they describe, so filters, joins, backups, and access control stay in one place [1].
  • sqlite-vec is a good fit for local tools, CLIs, and tests where a server is overkill [2].
  • A dedicated engine (Qdrant, Chroma, or a managed service like Pinecone) earns its keep when the corpus or query load grows well past what one Postgres instance handles comfortably, or when you need features like built-in hybrid scoring or multi-tenant collections out of the box [3][4][5].
  • Whatever you pick, put retrieval behind a small interface so you can swap the store later.

VERDICTStart with pgvector and an HNSW index on the existing Postgres. Re-evaluate when p95 query latency or index build time stops meeting the target, not before.

Why pgvector first#

Most of the team's queries filter by product and customer tier before ranking by similarity. With pgvector those filters are ordinary WHERE clauses on the same table, and permissions follow the rules the app already has. A dedicated store would need those attributes copied into its payloads and kept in sync.

CREATE EXTENSION IF NOT EXISTS vector;
ALTER TABLE chunks ADD COLUMN embedding vector(1024);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

SELECT id, title
FROM chunks
WHERE product = 'billing' AND tier = 'enterprise'
ORDER BY embedding <=> $1
LIMIT 10;

TIPBuild the HNSW index after the initial bulk load, not before, and raise maintenance_work_mem for the build. Both cut index build time noticeably [1].

When to move off it#

Plan a move to a dedicated engine if any of these hold for more than a few weeks:

  1. p95 retrieval latency exceeds the target after index tuning.
  2. Index builds or vacuum on the embeddings table interfere with the app's normal traffic.
  3. You need per-tenant isolation or replication patterns that are awkward in Postgres.

RISKEmbeddings from different models are not interchangeable. Changing the embedding model means re-embedding the whole corpus, whichever store you use. Record the model name and version with every vector.

Hybrid search#

Keyword matching still wins for exact identifiers such as error codes and SKUs. In Postgres, combine a full-text tsvector rank with vector similarity and merge the two result lists (reciprocal rank fusion is a simple, robust choice). Dedicated engines often provide this directly; check that their scoring is explainable enough for your support team.

WARNINGDon't judge options on public benchmark charts alone. Run your own queries against a sample of your own data, with your filters, and measure recall against a small labeled set.

Recommended next steps#

  1. Enable pgvector on a staging copy and embed a 10% sample of the corpus.
  2. Label 50 real support queries with the articles that should come back.
  3. Measure recall at 10 and p95 latency with and without filters; tune ef_search.
  4. Wrap retrieval in a search(query, filters) function so the store is replaceable.
  5. Log the result as an issue if it misses the target, and revisit Qdrant as the first alternative.
